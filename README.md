# СРС №3 — Professional Code Review

## Code Review & Vulnerability Analysis

В рамках СРС №3 был проведен Code Review программы, разработанной в СРС №1 и дополненной в СРС №2.

Цель анализа — найти реальные ошибки и потенциальные уязвимости, не нарушая существующую бизнес-логику программы: меню, контрольный вопрос и блокировку при неправильном ответе.


### 1. Некорректная обработка нечислового ввода

**Описание проблемы:**  
В исходной версии программы для получения пункта меню использовался прямой ввод:

```cpp
cin >> выбор;
```

Если пользователь вместо целого числа вводил, например `abc`, поток `cin` переходил в состояние ошибки. Из-за этого дальнейший ввод мог обрабатываться некорректно.

**Тестовый ввод:**

```text
abc
```

**Некорректное поведение:**  
Программа не получает корректное значение переменной `выбор`, а поток ввода переходит в состояние ошибки.

**Потенциальные последствия:**  
Пользователь может случайно ввести неправильное значение, после чего нормальная работа меню нарушается. В реальной системе это может привести к невозможности продолжить работу с программой.

**Предлагаемое решение:**  
Использовать отдельную функцию `readInt()`, которая принимает ввод как строку и проверяет, является ли введенное значение целым числом.

```cpp
stringstream ss(input);
int value;
char extra;

if (ss >> value && !(ss >> extra))
{
    return value;
}
```

Если преобразовать строку в целое число невозможно, программа выводит сообщение об ошибке и повторяет ввод.


### 2. Отсутствие проверки завершения потока ввода

**Описание проблемы:**  
Функция чтения данных работает внутри цикла `while (true)`. Если стандартный поток ввода неожиданно завершится (EOF), обычная операция чтения больше не сможет получить данные.

Проблемный вариант:

```cpp
cin >> input;
```

**Тестовое поведение:**  
Поток стандартного ввода завершается во время работы функции `readInt()`.

**Некорректное поведение:**  
Без отдельной проверки программа продолжает попытки получить данные из уже недоступного потока ввода.

**Потенциальные последствия:**  
Программа может перейти в некорректное состояние и не сможет нормально продолжить работу. Это снижает надежность программы.

**Предлагаемое решение:**  
Проверять результат операции чтения:

```cpp
if (!(cin >> input))
{
    cout << "\nВвод завершен. Программа будет остановлена.\n";
    exit(0);
}
```

Таким образом программа обнаруживает невозможность дальнейшего чтения и корректно завершает работу.


### 3. Отсутствие валидации ввода контрольного вопроса

**Описание проблемы:**  
В первоначальной версии контрольного вопроса использовался прямой ввод:

```cpp
cin >> ответ;
```

Контрольный вопрос ожидает целое число. Если пользователь вводит текст, поток `cin` переходит в состояние ошибки.

**Тестовый ввод:**

```text
hello
```

вместо ожидаемого значения:

```text
20
```

**Некорректное поведение:**  
Переменная `ответ` не получает корректного числового значения, поэтому дальнейшая проверка ответа становится ненадежной.

**Потенциальные последствия:**  
Пользователь может нарушить нормальную работу контрольного вопроса неправильным вводом. В результате блокировка, которая должна требовать правильный ответ, может работать некорректно.

**Предлагаемое решение:**  
Использовать ту же функцию `readInt()`, которая применяется для основного меню:

```cpp
ответ = readInt(
    "\nСколько часов в неделю обязан отрабатывать лаборант на 0,5 ставки? "
);
```

Таким образом меню и контрольный вопрос используют единый механизм проверки пользовательского ввода.


### 4. Жестко заданное значение нормы рабочего времени

**Описание проблемы:**  
В программе значение нормы рабочего времени `20` используется непосредственно в логике проверки:

```cpp
if (ответ != 20)
{
    cout << "Неверно! Повторите ввод.\n";
}
```

Число `20` в данном случае является магическим числом. Это бизнес-правило программы, которое записано непосредственно внутри условия.

**Тестовое поведение:**  
Предположим, что норма рабочего времени изменяется с `20` до `18` часов.

Разработчик может изменить текст:

```text
На 0,5 ставки — 18 часов в неделю.
```

но забыть изменить:

```cpp
if (ответ != 20)
```

**Некорректное поведение:**  
Программа будет показывать пользователю одну норму рабочего времени, но контрольный вопрос продолжит проверять другое значение.

**Потенциальные последствия:**  
Это может привести к неправильной проверке рабочего времени и появлению противоречивой информации в разных частях программы.

**Предлагаемое решение:**  
Хранить норму рабочего времени в одной именованной константе:

```cpp
const int WEEKLY_HOURS = 20;
```

После этого использовать ее в проверке:

```cpp
if (ответ != WEEKLY_HOURS)
{
    cout << "Неверно! Повторите ввод.\n";
}
```

При изменении нормы потребуется изменить значение только в одном месте.


### 5. Недостаточная проверка диапазона пунктов меню

**Описание проблемы:**  
Функция `readInt()` проверяет, является ли введенное значение целым числом, однако сама по себе не проверяет, существует ли такой пункт меню.

Например, пользователь может ввести:

```text
999
```

Число `999` является корректным целым числом, поэтому `readInt()` его принимает, хотя пункта `999` в меню не существует.

**Тестовый ввод:**

```text
999
```

**Некорректное поведение:**  
Значение передается в конструкцию `switch`, после чего программа попадает в ветку `default`.

**Потенциальные последствия:**  
При дальнейшем расширении программы отсутствие централизованной проверки диапазона может усложнить контроль пользовательского ввода и увеличить вероятность логических ошибок.

**Предлагаемое решение:**  
После получения значения дополнительно проверять допустимый диапазон:

```cpp
if (выбор < 0 || выбор > 6)
{
    cout << "Ошибка! Выберите пункт от 0 до 6.\n";
    continue;
}
```

После такой проверки в `switch` будут поступать только допустимые значения меню.


## Вывод

В ходе Code Review были выявлены пять проблем:

1. Некорректная обработка нечислового ввода.
2. Отсутствие проверки завершения потока ввода.
3. Отсутствие валидации ввода контрольного вопроса.
4. Использование жестко заданного значения нормы рабочего времени.
5. Недостаточная проверка диапазона пунктов меню.

Предлагаемые исправления повышают надежность программы и при этом сохраняют ее первоначальную бизнес-логику.

Меню продолжает выполнять свои функции, контрольный вопрос сохраняется, а при неправильном ответе пользователь по-прежнему должен повторить ввод.

Таким образом рефакторинг устраняет найденные проблемы, не удаляя уже работающие возможности программы, что соответствует принципу «Don’t throw the baby out with the bathwater».

## Модули СРС №2

В рамках СРС №2 исходная программа СРС №1 была дополнена тремя новыми модулями без удаления старой функциональности.

### 1. Учет рабочего времени

Модуль запрашивает количество рабочих дней, ставку и количество рабочих часов в день.

Для сценария используется:
- 5 рабочих дней;
- ставка 0.5;
- норма — 4 часа в день;
- итоговая норма — 20 часов в неделю.

Если пользователь вводит 2 часа в день, программа сообщает о дефиците рабочего времени и блокирует дальнейшее выполнение модуля до ввода 4 часов.

### 2. Дисциплинарные взыскания

Модуль запрашивает номер ноутбука и формирует описание инцидента, связанного с самовольным выносом настроенного учебного ноутбука за пределы кабинета и срывом учебного процесса.

Программа выводит структурированную дисциплинарную оценку произошедшего.

### 3. Протокол реагирования на саботаж

Модуль последовательно выполняет пять этапов:

1. Фиксация нарушения.
2. Уведомление руководства.
3. Проверка доказательств.
4. Подготовка служебной записки.
5. Передача материалов для рассмотрения возможных административных последствий.

Между этапами используются задержки через `std::this_thread::sleep_for`.

## Компиляция и запуск

Для компиляции программы используется команда:

```bash
g++ main.cpp -o bot -pthread
```

Для запуска программы:

```bash
./bot
```

Параметр `-pthread` необходим для корректной работы модуля, использующего `<thread>` и `std::this_thread::sleep_for`.
